# Architecture

## Design objective

The Harness tries to convert extra local inference time into higher coding reliability. It does not ask several identical agents for votes and call the majority correct. Instead, it separates responsibilities, persists evidence outside model context, executes deterministic checks, and permits a change only after verification and review.

## Components

### OpenCode orchestrator

OpenCode is the user-facing interface. A generated project-local configuration connects it to the Harness over MCP and to the local model through the guarded gateway. The main agent can start, wait for, inspect, apply, cancel, and resume coding runs.

### Shared model gateway

Every OpenCode and Harness request passes through one semaphore. The default maximum is four concurrent requests. The gateway also:

- restricts requests to the configured model;
- normalizes reasoning controls;
- counts the actual local tokenizer and chat template;
- enforces context and output limits;
- records active, waiting, completed, and failed requests;
- never silently retries an uncertain inference request.

### Isolated workspace

Each run snapshots allowed project files into a private worktree. Secrets, model weights, Git metadata, virtual environments, dependencies, and common build products are excluded. Roles can only write within both the project-level allowlist and their task-level ownership.

### Role pipeline

| Role | Access | Responsibility |
| --- | --- | --- |
| Explorer | read-only | map relevant files, entry points, contracts, and tests |
| Test Designer | read-only | identify acceptance checks, edge cases, and regressions |
| Specialist | read-only | inspect interfaces, complexity, security, or domain risks |
| Planner | structured output | create 1–4 implementation tasks with exact write ownership |
| Implementer | scoped write | modify owned files and add tests |
| Debugger | project write | diagnose real check/review failures and make minimal repairs |
| Reviewer | read-only | review task, full source, diff, and verification evidence |

Research roles run concurrently. Implementers run concurrently only when their write scopes do not overlap. The Harness serializes overlapping plans.

### Deterministic verification

Checks are argv arrays configured in `.agent-project.json`; they are not arbitrary shell strings generated by the model. On macOS they run through `sandbox-exec` with network denied and writes limited to the copied workspace and temporary directory.

The Harness hashes all source files before and after each check and rejects checks that mutate source code.

### Repair loop

When checks fail or Reviewer requests changes, the Debugger receives the structured verification and review evidence. Checks run again after each repair. The default maximum is three repair rounds.

### Guarded apply

An approved run stores a verified file manifest and diff. Application stops if:

- the candidate changed after verification;
- the user changed a target source file after the snapshot;
- a changed path is outside configured permissions;
- the candidate attempts automatic deletion.

Existing files are backed up before replacement.

## Persistence and recovery

Each run stores JSON checkpoints, role messages, events, checks, diff, usage, and recovery state under `.state/runs`. A service restart marks in-flight jobs interrupted; the user can explicitly resume them without discarding completed checkpoints or resetting consumed budgets.

## Current architectural limitations

1. Research roles are fixed and all three must finish before planning.
2. Test Designer findings are advisory; they are not yet automatically converted into protected executable tests.
3. Independent review means independent context, not an independent model family.
4. File ownership catches path overlap but not every semantic interface conflict.
5. The current runner is macOS-specific and not VM-grade isolation.
6. No automatic file deletion or rename is supported.
7. No built-in Git-history, browser, database, container, or dependency-installation tools are exposed.
8. Context compaction preserves a ledger but cannot recover information never written to files or checkpoints.

These limitations define the near-term work in [ROADMAP.md](../ROADMAP.md).
